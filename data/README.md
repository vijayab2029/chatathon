# Data artifacts

All files in this directory are **SIMULATED DATA** — synthetically generated for
this demo, deterministic (`random.seed(42)`), no real people, no real WHOOP
account, no real calendar. Regenerate with the scripts in `scripts/`.

| File | Generated by | Scope |
|---|---|---|
| `synthetic_calendar.json` | `scripts/part2_calendar/analyze_calendar.py` | Per-person, private |
| `meeting_features.json` | `scripts/part2_calendar/analyze_calendar.py` | Per-person, private |
| `team_structural_summary.json` | `scripts/part2_calendar/analyze_calendar.py` | De-identified, employer-safe |
| `whoop_biometrics.csv` | `scripts/part1_biometrics/generate_biometrics.py` | Per-person, private |
| `stress_scores.csv` | `scripts/part1_biometrics/generate_biometrics.py` | Per-person, private |

Cohort and window must stay in sync across generators: `user_101`–`user_106`,
`2026-09-13` to `2026-09-19`.

## Important for Part 3 (correlation/insight engine): the join is lagged, not same-day

WHOOP recovery/HRV/RHR are measured overnight and reported the *next* morning, so
that's how this data was generated: a `whoop_biometrics.csv` / `stress_scores.csv`
row for date **D** reflects `meeting_features.json`'s row for date **D-1**, not D.
Today's meeting load only drives today's `strain` (same-day, in `whoop_biometrics.csv`).

**When joining `meeting_features.json` against `stress_scores.csv`/`whoop_biometrics.csv`,
shift the calendar side back one day** (features for D-1 explain recovery/stress on D).
Joining same-date will find a much weaker, noisier relationship than what's actually
in the data — the generator verified a same-cohort lag-1 correlation of **-0.98**
(prior-day meeting load → next-day recovery); a same-day join won't reproduce that.

Part 4 and 5 don't need this detail — they only ever consume `team_structural_summary.json`
(de-identified) and whatever aggregate/insight output Part 3 produces, never the raw
per-person biometrics or the lag mechanic directly.
